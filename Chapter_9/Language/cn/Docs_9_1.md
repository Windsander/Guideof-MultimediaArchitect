
# 9.1 现代流媒体链路全景（The Streaming Pipeline）

前八章带着我们跟着比特走了一路：压缩、打包、运输、拆包、播放。这条路走通之后，一个自然的问题浮上水面，当这条路不再服务一个观众，而是同时服务千万个观众，它会变成什么模样？答案是：**路会变成网，机器会组成链路**。

一场真实的直播，没有任何一台设备能独自完成。摄像头只管采集，推流端只管发车，源站只管接单，转码集群只管改制，CDN 只管分发，播放器只管落地，每个环节都是专职的接力手，也都可能是专属的故障源。看懂这条链路，是流媒体工程师从 "写代码" 走向 "管系统" 的第一步。

本节按 "旅程 → 延迟 → 故障 → 分工 → 预算 → 容灾" 的顺序递进：

- **[9.1.1 一场直播的完整旅程](Docs_9_1_1.md)**：从采集到播出的七站接力，每一站谁在值守、交出什么样的接力棒
- **[9.1.2 端到端延迟：从采集到视网膜](Docs_9_1_2.md)**：glass-to-glass 的权威定义与延迟四级分类；为什么 1 秒延迟如此之难
- **[9.1.3 链路各环节的角色与故障域](Docs_9_1_3.md)**：把 "卡了" 两个字拆到具体环节，每个环节坏起来各是什么模样
- **[9.1.4 协议在链路两端的分工](Docs_9_1_4.md)**：回收第七章的协议群像，为什么推流端与拉流端从来不用同一种语言
- **[9.1.5 延迟预算：glass-to-glass 的定量拆解](Docs_9_1_5.md)**：把总延迟拆成逐环节的账；三条管线（HLS/LL-HLS/WebRTC）的毫秒都花在哪
- **[9.1.6 多 CDN 调度与容灾](Docs_9_1_6.md)**：DNS/302/SDK 三种调度姿势；冷缓存风暴与切换代价；为什么没有厂商敢承诺 100%
